# ADR #88: The theme registry is a dock panel, its destination is decided in Rust, its packages are verified, and the library splits from the palettes by *shape*

The Open VSX browser adds the app's first outbound traffic to a third party it does not control, and three decisions carry that: the registry URL is read from preferences **inside the command** and never accepted as an argument, a download URL is checked against that registry's origin before anything is fetched, and the bytes are verified against the digest the registry publishes. On disk, `installed_themes.json` takes the editor themes and the update metadata while the palettes stay in `localStorage` — split by shape, not by size. See ADR #87 for the conversion this sits on top of.

**Decision:** The registry browser is a right-dock panel; the registry URL is read from ThemePrefs inside the command, download URLs are checked against its origin and verified against the published sha256, and installed_themes.json holds editor themes and update metadata while palettes stay in localStorage.

**Alternatives rejected:**

- A workbench-tier dialog opened from Settings → Appearance — rejected for three stacked modals and an undiscoverable entry point.
- A compulsory variant picker on install — rejected; auto-pairing takes the first variant per side.
- Matching installed themes to registry rows by display name — failed; namespace/name is the join key.
- A command that accepts a registry URL from the frontend — rejected because it would bypass the kill-switch.
- A contains/ends_with host check — rejected because lookalike hosts would pass.
- Refusing versions without a published digest — rejected as gating on the check rather than strengthening with it.
- Downloading each .vsix to filter icon themes — rejected; the separately served manifest is fetched instead.
- Caching failed manifest fetches — rejected so a transient 503 does not hide a theme for 15 minutes.
- LazyLock — not usable under the crate's MSRV 1.77; OnceLock used.
- A strict semver parse for version comparison — rejected because 'cannot parse' must never mean 'no update'.
- Storing Monaco themes in localStorage — rejected; split by shape since they tolerate arriving late.

## Detail

**The browser is a dock panel, and the dialog it replaced failed for two independent reasons.** The first build put it in a `workbench`-tier dialog opened from Settings → Appearance. Installing anything then meant three stacked modals — settings, browser, variant picker — because the variant picker cannot be avoided: an extension contributes several themes and nothing says which light and dark variants are counterparts. And the only entry point was a small `IconButton` in the theme list's header, the same shape of affordance that had already made the local `.vsix` import hard to find. As the fourth occupant of the right dock (`RightPanelId`, alongside Saved/Pulse/AI) it gets a labelled activity-bar button and sits beside the workspace the way VS Code's own does. It follows that dock's existing contract exactly: deferred mount on first selection, kept mounted afterwards, and `active` — not mountedness — is what gates fetching, so a user who never opens it never issues a request.

**Installing asks nothing, because for most extensions there is no question.** The picker was compulsory in the first build and that was wrong: the answer is almost always "the light one and the dark one", so it made a one-click action a three-step one. `autoPairVariants` takes the **first** contribution on each side — a manifest's order is the author's own, which is why `GitHub Light Default` precedes its high-contrast sibling and `Dracula Theme` precedes `Dracula Theme Soft` — and a side with no contribution is left undefined so `buildThemeImport` duplicates rather than invents. The picker remains reachable per row, for the person who wants Gruvbox Dark Hard rather than Medium, and is always used for an **update**, which must rebuild the pairing that was installed rather than re-guess it (falling back to the automatic pairing when a recorded variant no longer exists in the new version). The picker also lost its name field: the package already carries a name, and asking the user to restate a correct value before continuing is a step that buys nothing.

**An installed theme is matched to a registry row by `namespace`/`name`, and matching it by display name did not work.** The first version compared the family's name against the row's `displayName`, which failed two ways: the name recorded at install comes from the *package manifest* while the row shows the *registry's* display name, and nothing requires those to agree; and renaming a theme in Appearance made it stop recognising itself. The join key was on disk the whole time and simply was not reaching the frontend — `ImportedEditorThemes.source` now carries it, hydrated from `installed_themes.json`. `findInstalledFamily` lives in `lib/vscodeTheme/` rather than in the panel so it can be tested without mounting anything: it is a join between two stores, not a rendering concern.

**A theme imported from a local `.vsix` is reconciled on its manifest identifier, which required measuring that the two naming schemes agree.** Such a theme has no registry origin at all, so without this, downloading Dracula by hand and then opening the panel offers it as if it were not installed. `InstalledTheme::identifier` records the manifest's `publisher.name` for *every* install, and it matches the registry's `namespace.name` — checked against the live service across thirteen colour themes, where the two were identical every time, and compared case-insensitively anyway since a namespace may be capitalised differently in one place than the other (`GitHub`). `InstalledTheme::version` is recorded beside it for the same reason: `check_theme_updates` needs something to compare a registry's latest against, and `ThemeSource::version` only exists for a registry install. With both, a hand-imported theme is checked against the *configured* registry — "not found" being an ordinary answer for one that registry does not carry — instead of showing as installed while silently never updating. `upsert` preserves both fields when an incoming record does not know them, the same protection `palette_edited` gets.

**The search runs once per session rather than on every activation.** `loadedOnce` guards it: switching the dock back to a panel that already holds results would re-spend someone else's bandwidth to redraw what is on screen.

**The frontend never names the destination, and this is ADR #71's rule applied unchanged.** `search_registry_themes` takes a query, not a URL; `registry_base()` reads `ThemePrefs` and refuses when `registry_enabled` is false. A command that accepted a URL would be a command that bypasses the kill-switch, and a preference only the UI honours is not a preference. The same reasoning that keeps `ai::provider::request` the sole addresser of an inference endpoint applies to a package registry for the same reason: the guarantee has to live where it cannot be routed around.

**A download URL arrives inside a record rather than being derived, so it is checked.** `RegistryTheme.download_url` comes back from a search and is then carried through state, a dialog, and possibly a stale update record. `ensure_same_origin` compares scheme, host and port against the configured registry before the fetch. Without it, "install this theme" means "fetch whatever host this record happens to name" — and the tests pin the lookalike cases (`open-vsx.org.evil.example`, `notopen-vsx.org`) that a `contains`/`ends_with` check would have waved through.

**The published `sha256` is verified, and a version without one still installs.** Every version publishes a digest next to its `.vsix` and it was confirmed to match byte for byte, so checking costs one small request. A mismatch is a hard failure — the bytes are not what the registry says they are, and both explanations for that end with "do not open this". A *missing* digest is not a failure, because refusing older extensions the registry serves happily would be gating on the check instead of strengthening with it.

**The `Themes` category contains icon themes, and only the manifest tells them apart — which is affordable only because the manifest is served separately.** The manifest is 1–11 KB at `/api/{ns}/{name}/latest/file/package.json`, so `search` fetches one per candidate (six at a time) and drops anything whose `contributes.themes` is empty. **A search hit does not carry `files.manifest`** — only the per-extension metadata response does — so that URL is the route every result actually takes, which is worth knowing before reading the code, where it is written as a fallback. Material Icon Theme — the most-downloaded item in the category — costs 11 KB to discard instead of 6 MB. The ROADMAP originally recorded that this filter "means reading the `.vsix`"; that was wrong and was corrected before the code was written, which is the only reason the design is not built around downloading every candidate.

**The result count is an upper bound and the UI must say so.** `totalSize` counts the category's hits, not the colour themes among them, and an exact count would mean fetching every manifest in the whole result set. A page of 24 hits routinely yields a dozen rows — a live search for "dracula" returns 10 colour themes out of ~51 hits.

**The manifest cache is manners, not optimisation.** Filtering one page costs 25 requests, and the registry publishes neither `Cache-Control` nor `ETag`, so there is nothing to revalidate against and no shared cache doing this for anyone. Without a local one, paging back or retyping a query re-fetches everything from someone else's free infrastructure. It is memory-only with a 15-minute TTL, and **failures are never cached**: the registry's 503s are transient, and remembering one would turn a blip into fifteen minutes of a theme mysteriously absent from the results. `OnceLock`, not `LazyLock` — the latter is stable since 1.80 and this crate's MSRV is 1.77, which `clippy::incompatible_msrv` enforces.

**`installed_themes.json` splits from `localStorage` by shape rather than by size.** A palette is 30 hex values that must be read *synchronously before first paint* or the app flashes the wrong theme, so it stays in `localStorage`. A Monaco theme is ~20 KB (One Dark Pro's 275 rules), is exactly what `localStorage` should not accumulate once a registry can install a dozen, and **tolerates arriving late** — `registerImportedMonacoThemes` defines whatever it is handed whenever it is handed it, so an editor that mounted first is repainted rather than broken. `hydrateInstalledThemes` runs from an ordinary `useEffect` for that reason, and also migrates anything a pre-split build left stranded in `localStorage`. The in-memory copy survives in the store only because the Preferences picker has to re-render when a theme is installed, and React cannot subscribe to a file.

**`palette_edited` is what makes an update safe, and `upsert` preserves it even when the incoming record clears it.** The editor half can always be replaced — nobody hand-edits 275 token rules — but a derived palette the user has touched is theirs. An update that silently overwrote someone's colour work would be the worst failure this feature could have, so the flag is set on the first edit of an imported theme's colour and never cleared by an update. The browser turns it into two visibly different outcomes rather than one button that quietly behaves differently.

**Version comparison is deliberately not a semver parse, and its first version had a bug the tests caught.** `is_newer` originally split on `.`, `-` and `+` together, which makes two correct rules contradict: a missing component makes a version older (`1.2` < `1.2.1`) while a missing pre-release tail makes it newer (`1.2.0` > `1.2.0-beta`). The release-beats-prerelease case lost. Core and tail are now split first and compared under their own rules. A strict semver parse was rejected because extension versions are `major.minor.patch` by convention and not by rule, and "cannot parse" must never resolve to "no update available" — a silent failure nobody would report.

**`ThemePrefs::registry_enabled` defaults to `true`, against the rule that a new flag starts off (ADRs #58, #83), and the exception is argued rather than assumed.** Those flags are per-connection and guard a *database*: leaving one on would expose a server the user never offered. Nothing of the user's leaves the machine here — anonymous GETs for public packages, no credentials, no telemetry, no schema — and the app already makes outbound requests for the updater and the issue reporter, so this is a new destination rather than a new capability. `registry_url` exists for the installs that are not on open-vsx.org (a company's own instance) or not on any network at all, and it is stored **per installed theme** as well, so changing the preference cannot silently re-target an update at a different registry's extension that happens to share a name.
