# ADR #55: The schema tree filter never opens connections and has one owner

Typing only searches what's already loaded in `useSchema` (warming further is an explicit button); `treeMatches.ts` distinguishes pending/unloaded/none/matches/out-of-scope instead of a misleading `0`, and `useTreeSearch` is deliberately its own ephemeral, non-persisted store.

**Decision:** The tree owns the search and hands results down: typing searches only what useSchema already holds, warming further is an explicit button, treeMatches returns pending/unloaded/none/matches/out-of-scope, and the search lives in its own non-persisted useTreeSearch store with one 180 ms debounce.

**Alternatives rejected:**

- Bounded per-keystroke prefetch that opened a database-view pool per unloaded database: rejected because it could exhaust a shared server's connection limit and skipped persistence subscriptions.
- Scope chip inside the filter box: rejected because at the panel's docked width it left about eight characters of input visible.
- Search fields on useUi: rejected because they invite being added to the persisted LaunchView/LaunchState contract.
- Per-explorer debounce with a raw string passed down: rejected because it filtered contents and the database list by different needles for 250 ms.
- Recording search folds in useUi.collapsedConnections: rejected because that set is persisted and would leave permanent folds.

## Detail

**Typing in the schema tree's filter must never open a connection — and the search has exactly one owner, one debounce and one subscription.** The panel had one filter box that silently applied only to `useUi.selectedConnectionId`'s subtree (`ConnectionsTree` passed `""` to every other connection), so with two connections open one filtered and the other did not, with nothing on screen to explain it — the only marker of "selected" is a 2px hairline, and the selection moves on its own when a tab opens or the palette navigates. Below that sat a second, equally invisible scope: `MultiDbExplorer`'s local `activeDatabaseName`, set as a side effect of expanding a database, which also collapsed its siblings. The redesign inverts the data flow — the tree owns the search and hands *results* down instead of a raw string — and the pieces below are each load-bearing:
    - **Typing opens no pools.** `MultiDbExplorer` used to run a bounded prefetch off its debounced needle: every keystroke walked the databases it had not loaded and opened a `<parent>::db::<db>` view — a whole connection pool — for each. The bound (three at a time, 1.13.0) made it survivable, not right: the unbounded version was itself enough to exhaust a shared server's limit on a nineteen-database box, against a server the user shares with their application, their IDE and any MCP sidecars. A search now reads only what is already in `useSchema`; reaching further is a button on the filter box (`lib/schema/warmForSearch.ts`), which says how many databases it will load and why. **This is the invariant a future performance pass would cheerfully undo**, so it is stated at the top of that file too. It also fixed two silent bugs for free: the prefetch used the bare `api.openDatabaseView` while `warmDatabases` uses `openTrackedDatabaseView`, so a database warmed by searching never got its persistence subscription (ADR #27); and it applied the visible-databases subset in the warm loop but not in the "are we still prefetching?" check, which is the next bullet.
    - **`0`, "still loading", "never read" and "not searched" are four different answers, and only one of them is `0`.** The old code had one boolean (`prefetching`) computed over `cs.databases` *without* `visibleSet` while the loop that warmed them applied it — so with a subset active it was stuck true forever, `schema.noMatches` could never render, and the user got an empty tree with no explanation. `lib/schema/treeMatches.ts` now returns `pending` / `unloaded` (cold) / `none` / `matches` / `out-of-scope`, in that precedence, and a provisional `0` is what makes someone abandon a search that would have worked.
    - **The scope chip lives on the status line under the box, not inside it.** In the box, in front of the caret, it was the more obvious design and it did not survive contact with the width this panel is actually docked at: a chip reading `Dev | Tencer | MySQL · iMesPyme` left about eight characters of input visible. The flex maths made it worse than it had to be — the input carries `flex-1 min-w-0`, so it is the first thing to shrink and the chip won the space outright — but shoring that up with minimum widths just trades a squashed input for an unreadable chip in a box that has room for neither. Out on the status line it shares a wrapping row with the match summary, so on a narrow panel it takes the line it needs instead of taking it from the input, and it can name a connection *and* a database. Consequence worth keeping straight: the two ✕ affordances now clear what they sit next to (box → the needle, chip → the scope), where a single in-box ✕ used to drop both. `clear()` still drops both and is what entering an environment calls.
    - **`useTreeSearch` is its own store, deliberately not three fields on `useUi`.** `useUi` owns the three *persisted* view filters and their `LaunchView` contract (convention #45); an ephemeral search sitting among them is an invitation to add it to `LaunchView` → `LaunchState` → the Rust struct, where it either vanishes at the IPC boundary (gotcha #14) or — worse — does not: a restored needle would paint every connection folded with a `0` badge for the length of the launch reconnect. Nothing here is persisted, and the scope is safe to keep in memory only because `clear()` drops it together with the needle, so a scope can never outlive the search that motivated it. `pendingChord.ts` is the precedent for the shape.
    - **`patterns`, not a string, is what travels down.** `matchesFilter` split/trimmed/lowercased the needle once per table per render; on a large catalogue that allocation, not the `includes`, is the dominant cost of a keystroke. It is parsed once in `commit()`, and `commit` keeps the previous array's *identity* when the needle is unchanged — which is what lets the explorers depend on it. Same move one level up: `useTreeMatchCounts` holds the app's only subscription to `useSchema.byConnection` (there used to be one per explorer), safe as a raw selector for the usual reason (the store replaces slices, never mutates them, gotcha #1), with a `WeakMap` keyed on each slice's `tables` array caching the lowercased names — a self-invalidating cache key for free.
    - **One debounce, in the box.** Each `MultiDbExplorer` had its own, and `DatabaseRoot` was handed the *raw* filter while the database list was chosen by the debounced one, so for 250 ms after each keystroke the tree filtered its contents by a different needle than the one that decided what to show. With no string travelling as a prop that state is unrepresentable. 180 ms, not 250: the old value existed to throttle pool opens, not renders.
    - **A filter's fold is visual and ephemeral.** It must never touch `useUi.collapsedConnections` — that set goes through `persistLaunchState`, so folding by search would leave permanent folds in the environment's `LaunchState` that nobody asked for. The automatic fold is component-local and evaporates with the needle; the chevron still works, as an override that lasts as long as the search.
    - **The filter never hides a connection row**, only dims and folds it: those rows are what the user needs in order to connect one or narrow the search to it.
    - `data-kb-scope="tree"` lives on `ConnectionsTree`, not `SchemaExplorer`. Declared on the explorer it covered only an *expanded* connection's subtree — the filter box and every row were outside it, i.e. the two places a `tree` binding is most likely pressed. Related: `focusTreeFilter` is scoped `global` on purpose, since a `tree`-scoped binding is only audible from inside the panel and could never be the thing that takes you there.
