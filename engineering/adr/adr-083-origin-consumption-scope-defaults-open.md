# ADR #83: An origin's consumption scope is the one per-resource flag that defaults to ON

`OriginScope` lets each machine subscribe to a subset of a shared origin's document (connections / environments / JSON Schemas), which removes the reason a team kept a second connections-only file. Its three fields default to `true` — against the house rule for per-resource opt-ins — because the field describes what an origin was *already* pulling, and a closed default would make the first sync after an update report the user's whole configuration as vanished.

**Decision:** Each machine subscribes to a subset of a shared origin via `tab_state::OriginScope` (connections / environments / JSON Schemas), every field defaulting to true per field, with gates in `sync_origin_inner` and non-destructive narrowing.

**Alternatives rejected:**

- Splitting the document into an environments file referencing a connections file by path — rejected because it institutionalises two files, adds a breakable cross-file reference, a second concurrency domain and an ownership question origin_id cannot answer.
- Closed (false) defaults like other per-resource opt-ins — rejected because the first sync after updating would report every environment as vanished.
- `#[serde(default)]` on the struct only — rejected because a partially-written object would fill missing fields with false.
- Clearing the origin tag when a slice is unticked — rejected because detaching is irreversible (connections never re-adopted, environments duplicated).
- Gating inside the merge functions — rejected; gates live in sync_origin_inner so a narrowed scope is not read as 'found nothing'.
- Asking for the scope blind without previewing the file — rejected in favour of peek_origin_file returning counts only.

## Detail

**A shared origin is one file with N subscriptions, and the subscription lives on the consumer.** The reported problem was a team maintaining two published files — one carrying environments *and* connections, one carrying connections only — because half of them already had their environments set up and did not want somebody else's. The two files then drifted, since nothing kept the second in step with the first. Splitting the document (an environments file referencing a connections file by path) would not have fixed that: it institutionalises the two files and adds a cross-file reference that can break, a second concurrency domain with no transaction over the pair, and an ownership question `ConnectionProfile.origin_id` — a scalar, and the whole ownership model — cannot answer. What the case actually needed was a *filter on the consumer*, which makes the divergence impossible by construction: the publisher always publishes the superset, and each machine decides what it reads. `tab_state::OriginScope` is that filter, and it sits beside `Origin::role` because it is the same kind of thing — this machine's own decision about somebody else's file, never something the document can dictate.
    - **Every field defaults to `true`, and that inverts ADR #58 on purpose.** Every other per-resource opt-in here is closed until the user says otherwise (`mcp_exposed`, `pulse_enabled`, `ai_enabled`), because those are *permissions* and a profile written by an older version must not be open. This one is a *description of what the origin was already doing*: an origin registered under 1.23 pulls all three slices. A closed default would narrow every registered origin on every machine the moment the update installs, and `sync_origin_inner` would then hand `sync_environment_bundles` an empty list — which is authoritative, not empty-therefore-skip — so a machine mirroring fewer than `SUSPICION_FLOOR` environments has no ratio check to save it and every one of them is reported vanished. The safe default for a permission and the safe default for a description of existing behaviour point in opposite directions; `an_origin_written_before_the_scope_existed_pulls_everything` and `a_team_sized_environment_set_would_be_reported_vanished_wholesale` are the pair that pins it.
    - **The `default` is per field, not on the struct.** `#[serde(default)]` on `OriginScope` itself only covers the field being absent *as a whole*; a partially-written object fills the rest with `bool::default()`, which is `false`, and quietly reproduces the failure above. Each field carries `#[serde(default = "enabled")]` instead. Same trap, same shape as gotcha #14 — serde's silence is the hazard in both directions.
    - **Narrowing a scope is deliberately non-destructive, and it has to be, because detaching is irreversible in two *different* ways.** Untick a slice and what it already landed stays put: still tagged with the origin, still read-only in the UI, simply no longer refreshed. Clearing the tag instead is a separate, explicit act, because `merge_into` skips a profile whose `origin_id` no longer names this origin (`continue` — "a local profile that happens to share an id is the user's, not the file's"), so a detached connection can never be re-adopted; while `sync_environment_bundles` matches on `origin_id` + `origin_source_id`, so a detached environment is *duplicated* on the next pull rather than skipped. One checkbox must not be able to reach either outcome, and the edit form says so in words.
    - **The three gates go in `sync_origin_inner`, never inside the merge functions.** `sync_environment_bundles`' contract is "reconcile these bundles against what this origin owns"; a narrowed scope means there is nothing to reconcile *against*, not that the reconciliation found nothing. Same for `merge_profiles_bundle` — the `connections: false` arm returns `OriginSyncReport::default()` rather than merging an empty slice, so `landed_secrets` is carried through untouched and no disappearance is computed. The passphrase gate moved under the same condition: `meta.encrypted` describes the `profiles` section and nothing else, so an origin narrowed to environments or schemas must not be blocked on a passphrase it will never use.
    - **`OriginSyncReport::pulled` exists because every count is zero for two different reasons.** "The file publishes no environments" and "this machine does not pull environments" are not the same news, and a summary that conflates them tells a user who deliberately switched environments off that they got `0 environments`, which reads as the feature being broken.
    - **The scope picker previews the file (`peek_origin_file`) rather than asking blind.** It repeats `sync_origin_inner`'s two-step parse — peek `meta.kind`, then deserialise the matching shape — because `serde_json` drops unknown fields, so reading an environment file as the plain profile shape succeeds while silently discarding its whole `environments` array. A preview that disagrees with the sync about what a file contains is worse than no preview. It returns counts only: it renders under a path the user may have typed by mistake, and a preview must not become a way to read somebody else's file. Two combinations are warned about and none are forbidden — environments without connections mirror as empty, schemas without connections land every binding disabled — because each is correct for somebody (a publisher consuming their own document already holds the profiles).
